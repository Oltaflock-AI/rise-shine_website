01

System map

One Next.js deployment. Four external systems. The browser never talks to any of them directly — every credential-bearing call happens on the server.

Browser
pages / flights / hotels / packages client checkout forms, filters, autocomplete hosted Cashfree checkout v3 (popup)

▼ ▼ ▼

Next.js app
rsc server components — search pages call lib/ directly route handlers /api/* — Node runtime, force-dynamic proxy.ts session refresh + /account gate src/lib all integration + business logic src/data every word of copy

▼ ▼ ▼

Suppliers
TBO air Search · FareQuote · SSR · Book · Ticket TBO hotel static data · Search · PreBook · Book · Cancel Cashfree orders · order lookup · refunds · webhook Supabase auth · Postgres · storage Resend customer + ops email Google Places live reviews ElevenLabs voice-agent call log

The site is two products sharing one deployment. The marketing layer — packages, itineraries, services, enquiry forms — is content-driven and reads entirely from src/data/. The booking layer is a real OTA: it searches live inventory, re-prices it, charges a card, and issues a ticket. Everything careful in this codebase belongs to the second one.

Before you write framework code

Next.js 16 changed APIs and file conventions — including renaming middleware to proxy. Blog posts and memory are unreliable here. The authoritative docs for the exact installed version are in node_modules/next/dist/docs/. This is a standing project rule, recorded in AGENTS.md.

The content rule: words, prices, phone numbers and tour details change in src/data/, never in a component. Components read data; they don't own it. Business identity in particular is single-sourced in src/data/site.ts and consumed by the header, footer, contact page and the layout's JSON-LD.

03

The lib/ resources

API handlers are deliberately thin. They parse, rate-limit, delegate, and shape a response — the thinking lives here.

Flights — TBO

ModuleWhereOwns
tbo.ts server Auth-token cache and Search. Normalizes raw results into FlightOffer — per-adult fares, de-duplicated, cheapest first. 10-minute result cache.
tbo-book.ts server The booking flow: FareRule → FareQuote → SSR → Book/Ticket → GetBookingDetails. LCC tickets in one step; non-LCC books then tickets. Owns timeouts and timeout recovery.
tbo-validate.ts server TBO's entire certification checklist — PAN/passport/GST rules, title normalization, special-fare seat and meal, the duplicate guard, per-passenger fare split.
tbo-fetch.ts server One wrapper routing every TBO call through an optional static-IP forward proxy (TBO_PROXY_URL).

Hotels — TBO, different hosts and different credentials

ModuleAuthOwns
tbo-hotel-static.ts static-data creds CountryList, CityList, TBOHotelCodeList, HotelDetails — the catalogue, photos and descriptions.
tbo-hotel.ts agency creds Search and PreBook. PreBook is the hotel analogue of FareQuote: authoritative re-price plus the rate's validation rules.
tbo-hotel-book.ts agency creds Book, guest validation, and recovery-by-reference when Book times out.
tbo-hotel-post.ts agency creds Post-booking: GetBookingDetail, GenerateVoucher, Cancel, cancellation polling.

04

API surface

Every handler runs on the Node.js runtime. Anything touching TBO is force-dynamic — never statically cached. The stripe on each row says what the call costs.

  • local or cached — cheap
  • calls the supplier — costs quota
  • moves money

Flights

GET
/api/flights
Search. from/to accept an IATA code or a city name, resolved server-side.
  • from · to · depart · return · adults · trip · max
  • rate limit 20/min
  • CDN s-maxage 1800
POST
/api/quote
FareRule + FareQuote. Returns the flags that tell the checkout form which fields TBO demands — PAN, passport, GST, mandatory seat or meal.
  • traceId · resultIndex · searchedAt
  • rate limit 15/min
POST
/api/payment/order
Runs the full pre-ticket flow, then opens a Cashfree order for TBO's re-priced total, tagged with a bind hash of the itinerary. A booking TBO would reject fails here — before the card is charged.
  • same body as /api/book, minus payment
  • maxDuration 120s
  • 422 = rule failure, nothing charged
POST
/api/book
Re-reads the order from Cashfree and requires PAID, then tickets. If ticketing fails after payment, it is refunded automatically and ops are alerted.
  • maxDuration 300s
  • 402 if the order is not PAID
  • mirrors to bookings · emails the lead passenger
POST
/api/payment/webhook
Cashfree server-to-server events into the payments ledger. Independent of the browser, which never sees a signed receipt — it records the money even if the customer closes the tab.
  • HMAC over the RAW body
  • PAYMENT_SUCCESS · PAYMENT_FAILED · PAYMENT_USER_DROPPED · REFUND_STATUS
  • 500 on write failure so Cashfree retries

Hotels

GET
/api/hotels/cities
Destination autocomplete from a bundled dataset. Short queries return the popular list.
  • rate limit 60/min
  • CDN s-maxage 86400
POST
/api/hotels
Search priced rooms. Pass explicit hotelCodes, or a cityCode — we resolve that city and price the first 100, TBO's per-request ceiling.
  • checkIn · checkOut · rooms[] · nationality
  • maxDuration 60s
  • rate limit 15/min
POST
/api/hotels/quote
PreBook — re-price and return the rate's validation rules. Forces PAN whenever the destination country isn't India, because TBO enforces it even when the rate doesn't flag it.
  • bookingCode
  • rate limit 15/min
POST
/api/hotels/payment/order
PreBook + guest validation against the rate's own rules, then a Cashfree order for the PreBook amount.
  • maxDuration 120s
POST
/api/hotels/book
Confirms the order is PAID, then Book. Auto-refunds on failure. Always carries a clientReferenceId — the recovery key if Book times out.
  • maxDuration 300s
POST
/api/hotels/cancel
Request a cancellation, or poll one. Auth required, and the booking must belong to the caller — checked against the account mirror, or any signed-in user could cancel arbitrary bookings by id.
  • bookingId · or changeRequestId to poll
  • 401 without a session

Platform

POST
GET
/api/voice/webhook
ElevenLabs post-call events into voice_calls: transcription, audio, initiation failure. The GET is a health check you can hit before pasting the URL into ElevenLabs.
  • HMAC over the RAW body · 30-min replay window
  • filtered by ELEVENLABS_AGENT_ID
  • maxDuration 60s
GET
/api/cron/reconcile
Weekly digest comparing the payments ledger against booking records, surfacing the failure that actually hurts: money collected with no booking on file.
  • Vercel cron 30 3 * * 1
  • Authorization: Bearer CRON_SECRET
  • 8-day window — one day of overlap
GET
/auth/callback
Exchanges a Supabase email-confirmation or OAuth code for a session, then forwards. The next parameter is path-checked against open redirects.
  • redirects to /account by default

Response conventions

StatusMeaningWho fixes it
200Success — always { ok: true, … }—
400Malformed body or a bad signatureCaller
401 / 402No session · payment required, or the order is not PAIDCaller
422A validation rule failed — the response carries ruleThe form can fix it and retry

One thing that catches people out: the search pages don't use these routes. /flights and /hotels are server components that call lib/ directly and stream results inside a keyed <Suspense> boundary, so the header and search bar paint immediately. The API routes exist for what the browser genuinely needs at runtime — checkout, autocomplete, live "from" fares, cancellation.

05

The booking flow

Collect, then fulfil. The order amount is always the supplier's re-price — never a number that came from the browser.

Search A server component calls searchFlights() and streams results. Offers are de-duplicated and sorted cheapest-first.
TBO · Searchreturns a TraceId — dead in 15 min
Quote The checkout form asks what this specific fare requires, rather than guessing. The answer drives which fields render.
TBO · FareRule → FareQuotePAN? passport? GST? seat? meal?
Validate, then open an order validateBooking() runs the entire pre-ticket sequence and every checklist rule, including the duplicate guard. Only if all of it passes does a Cashfree order open — for the FareQuote total, in rupees, bound to this itinerary.
TBO + Cashfreenothing charged yet
Customer pays Cashfree's hosted checkout opens as a popup and takes the money. Whatever it resolves with, the browser then calls the book route — a customer who pays and closes the popup must still get their ticket.
Cashfree · checkout v3order paid
Confirm the payment is real The browser proves nothing — Cashfree hands it no signed receipt. The server re-reads the order from Cashfree and checks it itself: order_status is PAID, the amount matches, and the bind tag matches this booking. Only then does any TBO call happen.
Cashfree · Get Order + Get Payments402 if anything is off
Ticket LCC fares ticket in one call; non-LCC book first, then ticket.
TBO · Book → Ticketnever auto-retried
Ticketed
  • Mirror the booking into bookings + passengers (signed-in users only)
  • Email the confirmation with the PNR to the lead passenger
  • Both awaited before responding — serverless can freeze the instant you return
  • Both wrapped in try/catch — neither may ever fail a paid booking
Not ticketed, but paid
  • Refund immediately — money is never held for a ticket nobody got
  • alertOps() so a human knows
  • Email the customer that the refund is on its way
  • If the refund itself fails: a loud URGENT alert for manual settlement

Why it's shaped like this

bookFlight() and validateBooking() share prepareBooking() — the pre-charge checks and the ticketing checks are literally the same code path. That's the whole design: anything TBO would reject at ticketing gets rejected before the card is touched.

Running alongside, the Cashfree webhook writes every successful, failed and refunded payment into the payments ledger independently of the browser. The weekly cron then compares that ledger against booking records. Guest bookings are never mirrored by design, so the digest reports those as "verify by hand" rather than pretending certainty.

06

Data model

Supabase Postgres, plain SQL migrations applied in order. Row Level Security is on everywhere; only server code holding the service-role key writes anything that matters.

TableWritten byContents and policy
profilestrigger on auth.usersName, phone, GSTIN. RLS: owner reads, inserts, updates.
travellersthe userSaved passenger details for faster checkout. RLS: owner, full access.
bookingsservice-roleFlights and hotels, distinguished by kind. Mirrors PNR / BookingId / status / fare plus the Cashfree ids. RLS: owner reads only.
passengersservice-rolePer-booking passengers and ticket numbers. RLS: readable through an owned booking.
enquiriesthe userPackage enquiries. RLS: owner reads and inserts.
paymentswebhookReconciliation ledger keyed by cf_payment_id: paid · failed · dropped · refunded, with method, contact and TraceId.
voice_callswebhookOne row per conversation — transcript, extracted lead fields, qualification. Audio lands in the private voice-call-audio bucket.

The mental model that matters

bookings is a mirror, not the source of truth. TBO owns bookings; we copy confirmed ones so the account page has something to show. Guest bookings — no session — are never mirrored, which is exactly why the reconciliation digest asks a human to check rather than declaring a problem.

bookings.status carries TBO's own itinerary status codes: 5 means ticketed, 6 means a cancellation has been requested.

07

Hard rules

Not style preferences. Each one exists because it broke real money, or would have.

  1. Server-only modules stay on the server.Never import tbo*, cashfree, supabase/admin, alerts or email from a client component. They read credentials from the environment. Reach them through /api/* or a server component.
  2. TraceId dies 15 minutes after Search.The search cache TTL is 10 minutes, deliberately under it. Don't lengthen it — a stale TraceId fails at Book.
  3. Match TBO errors by ErrorCode, never message text.Code 6 means an invalid token: refresh once and retry. This is TBO's explicit checklist rule.
  4. Book and Ticket are never auto-retried.On timeout, recover through GetBookingDetails — 20 polls at 12-second intervals. A retry double-charges. Hotels recover by clientReferenceNo.
  5. The charged amount comes from the supplier.FareQuote for flights, PreBook for hotels. Never a number from the request body.
  6. Never ticket on the browser's word.Cashfree hands the browser no signed receipt, so there is nothing client-side worth verifying. Re-read the order server-side and require order_status PAID, a matching amount, and a matching bind tag.
  7. Failed fulfilment after payment means refund now.Refund the payment amount, which can be under the order total on this API version — Cashfree rejects anything higher. And if the refund itself fails, alertOps() must fire. A failed refund can never be a console line nobody reads.
  8. On the server, verify with getUser(), never getSession().getUser() re-validates the token against Supabase.
  9. Keep useAuth()'s shape stable.Header, AuthScreen and AccountView all depend on { user, ready, login, signup, logout }.
  10. Only service-role server code writes bookings.Client access goes through RLS, which grants read-only access to a user's own rows.
  11. Next 16 renamed middleware to proxy.The file is src/proxy.ts, it exports proxy(), and it runs on the Node.js runtime. Don't create a middleware.ts.
  12. Webhook signatures are computed over the raw body.Read req.text() and verify before parsing — re-serializing the JSON changes the bytes and breaks the HMAC — Cashfree signs the timestamp plus the raw body, so 170.00 becoming 170 fails every signature. True for both Cashfree and ElevenLabs.
  13. Webhook status codes are an API.A write failure returns 500 so the sender retries. A bad signature or an unknown event is terminal.
  14. Await your best-effort side effects.Serverless can freeze the instant you return, so fire-and-forget writes get killed. Await them, wrapped in try/catch, so they can never fail a paid booking.
  15. All user-facing dates go through formatDate().DD-MM-YY. No raw ISO strings anywhere in the UI.
  16. Keep the legacy tour redirects in sync with catalogue slugs.Those 308s in next.config.ts preserve the old site's search rankings.

Config & degradation

The app boots with an empty .env.local. Every integration is gated on the presence of its keys, so nothing crashes — features simply switch off. That's what makes local development and CI possible without credentials.

Verify before you push

CommandWhat it proves

npm testVitest over the money paths: Cashfree webhook HMACs, TBO validations, booking parsing. Touch that code, add a test.

CI runs all three on every push and pull request, with lint non-blocking until the legacy errors are cleared.

09

Current state

Things that look like bugs but are decisions.

What you'll noticeWhy
Sign-in is switched off AUTH_DISABLED = true in src/lib/flags.ts. TBO's portal verification required booking to work without an account. Flipping it back restores the header auth UI, the login and signup screens and the checkout gate — no other change. Auth itself is fully built and working underneath.
Certification logs contain failures All seven flight cases and all eight hotel cases were ticketed or confirmed on the test environment. Some logs deliberately include failed supplier attempts next to the successful recovery — that is the evidence for the recovery path.
An odd forward proxy for TBO TBO whitelists caller IPs in production and Vercel has no fixed egress IP. When TBO_PROXY_URL is set, every TBO call routes through a static-IP proxy.
voice-agent/ is in the repo but never deploys It's a separate app, excluded via .vercelignore. The ElevenLabs webhook deliberately lives on the marketing site — the only deployed app with a public HTTPS URL and service-role database access. Nearly every lint error in the repo is inside that folder.
Enquiry forms post to a Google Form That is the entire lead pipeline today. No CRM, no email — marked TODO in the code.
Search pages bypass the API routes They're server components calling lib/ directly and streaming inside a keyed Suspense boundary, so the chrome paints instantly while results load.

Vocabulary

Supplier jargon appears everywhere in this codebase without explanation. Here it is once.

TermMeaning
TBO / TekTravelsThe supplier. Their API is the actual inventory — flights, hotels, ticketing.
TraceIdTBO's search-session id. Every later call quotes it. Dies 15 minutes after Search.
ResultIndexIdentifies one fare within a search result. TraceId + ResultIndex = "this specific fare".
LCCLow-cost carrier. LCC fares ticket in one step; non-LCC book first, then ticket.
FareQuoteTBO re-prices the fare and states what it requires — PAN, passport, GST, seat, meal. Authoritative.
PreBookThe hotel equivalent of FareQuote.
SSRSpecial Service Request — baggage, meals, seats.
PNRThe airline's booking reference.
PAIDCashfree's order status once the money is actually collected. Read from the server, never from the browser — we only ticket after the server has seen it.
RLSRow Level Security — Postgres policies deciding which rows a signed-in user may see.
CertificationTBO's live test-environment checklist that must pass before production credentials are issued. Complete for both flights and hotels.

When in doubt

If something in the payment or ticketing path looks wrong, ask before changing it. Most of the odd-looking code there is odd because a supplier or a payment gateway misbehaved once, and the comment above it usually says exactly how. Everywhere else — components, content, styling, the marketing site — dive straight in.
